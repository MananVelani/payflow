## 1. Service Overview

`worker-service` (C3) is a **stateless, horizontally scalable Go service** whose sole job is to execute payment tasks dispatched by the Coordinator (C2). It holds zero persistent state — all durable state lives in the Payment Log Service (C4). You can spin up one worker or fifty; the system behaves identically.

**What C3 does:**

- Registers with the Coordinator on startup and enters the live worker pool
- Streams incoming tasks from C2 over a persistent gRPC connection
- Consults C4 before touching the bank — idempotency first, always
- Calls the Mock Bank API, absorbs failures gracefully, and retries with backoff
- Reports a final `SUCCESS` or `FAILURE` result to C2 so C4 can be updated

**What C3 deliberately does NOT do:**

- Write to any database directly — C4 owns all payment state
- Make scheduling decisions — that's C2's domain
- Accept requests from external clients — C1 and C2 are the entry points

```
C2 (Coordinator Leader)
        │
        │  AssignTask (gRPC stream)
        ▼
 ┌─────────────┐     CheckIdempotency     ┌─────────────────────┐
 │   C3 Worker │ ─────────────────────►   │  C4 Payment Log     │
 │             │ ◄──────────────────────  │  Service            │
 └──────┬──────┘     (exists?, result)    └─────────────────────┘
        │
        │  HTTP POST /charge
        ▼
 ┌─────────────────┐
 │  Mock Bank API  │  (50–500ms latency · 10% random failure)
 └─────────────────┘
        │
        │  PaymentResult
        ▼
 C2 (Coordinator Leader)  →  C4 WriteResult
```

## 2. The "Exactly-Once" Pipeline

This is the critical path. Every step below is mandatory and ordered. Skipping step 2 is how you double-charge a customer.

### Step-by-Step Execution Flow

```
┌──────────────────────────────────────────────────────────────────────────┐
│  STEP 1 — Receive ProcessPayment from C2                                 │
│                                                                          │
│  C2 streams a task containing:                                           │
│    • task_id          (globally unique, generated by C2)                 │
│    • idempotency_key  (merchant-supplied or C2-generated UUID)           │
│    • amount, currency, merchant_id                                       │
│    • epoch            (C2's current epoch — stale tasks are rejected)    │
└────────────────────────────┬─────────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  STEP 2 — Call C4: CheckIdempotency(idempotency_key)                     │
│                                                                          │
│  ┌─ IF exists == true ──────────────────────────────────────────────┐    │
│  │  Return cached result to C2 immediately. DO NOT call the bank.   │    │
│  │  This handles: worker crash after bank success, coordinator      │    │
│  │  reassigning a task that already completed.                      │    │
│  └──────────────────────────────────────────────────────────────────┘    │ 
│                                                                          │
│  ┌─ IF exists == false ─────────────────────────────────────────────┐    │
│  │  Proceed to Step 3.                                              │    │
│  └──────────────────────────────────────────────────────────────────┘    │
└────────────────────────────┬─────────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  STEP 3 — Execute via Mock Bank API                                      │
│                                                                          │
│  POST /charge  {idempotency_key, amount, currency, merchant_id}          │
│                                                                          │
│  Mock Bank behaviour:                                                    │
│    • Latency:  50–500ms (uniform random)                                 │
│    • Failure:  10% random HTTP 500 / timeout                             │
│    • Idempotency: bank caches result by idempotency_key (safe to retry)  │
│                                                                          │
│  On FAILURE → trigger Retry Engine (see §4).                             │
│  On SUCCESS after retries exhausted → mark FAILURE, report to C2.        │
└────────────────────────────┬─────────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  STEP 4 — Report Final Result to C2                                      │
│                                                                          │
│  Send ReportResult(task_id, status, bank_txn_ref, worker_id)             │
│  C2 then calls C4.WriteResult() to persist the final state.              │
│                                                                          │
│  Note: if the worker crashes between Step 3 and Step 4, the next         │
│  worker assigned this task hits Step 2 and gets the cached bank result.  │
│  No double charge. See §4 for the full crash scenario.                   │
└──────────────────────────────────────────────────────────────────────────┘
```

## 3. Teammate Integration Points (API Contract)

### 3a. For Member 1 (C2 — Coordinator)

C3 maintains two active contracts with C2:

**Heartbeat** — C3 pings C2 every **2 seconds** on the `WorkerHeartbeat` stream.

| Field | Type | Description |
|---|---|---|
| `worker_id` | `string` | Stable UUID assigned at `RegisterWorker` |
| `load` | `float32` | Active tasks / total capacity (0.0–1.0) |
| `tasks_processed_count` | `int64` | Cumulative count since startup |
| `avg_task_duration_ms` | `int64` | Rolling average, used by C2 for weighted scheduling |
| `epoch` | `int64` | C2's epoch at last `AssignTask` — C2 uses this to detect stale workers |

> **If C2 misses 3 consecutive heartbeats (6s), it marks this worker DEAD and reassigns all in-progress tasks.** C3 must not assume C2 remembers it across a coordinator leader election — C3 re-registers on every coordinator reconnect.

**REVOKE Handler** — C3 exposes a `RevokeTask(task_id)` RPC. When C2 reassigns a task (because it suspects the worker is a "zombie" — alive but too slow), C2 sends `REVOKE`. C3 **discards the result** if the bank call completes after a revoke is received. The result is already being processed by a new worker; reporting a stale result would confuse C2 and create a duplicate `WriteResult` call to C4.

```
// Pseudocode — REVOKE guard in the execution goroutine
if revokedTasks.Contains(task_id) {
    log.Warn("task revoked mid-execution, discarding result", task_id)
    return  // do NOT call ReportResult
}
```

### 3b. For Member 3 (Proto — gRPC Layer)

C3 depends on the following gRPC methods defined in `worker.proto`. **These must be stable before M2 can do real work** — flag any schema changes in `#proto-changes` Slack before committing.

| gRPC Method | Direction | Description |
|---|---|---|
| `RegisterWorker(WorkerInfo)` → `WorkerAck` | C3 → C2 | Called on startup. C2 adds worker to the pool and begins sending tasks. |
| `ProcessPayment(Task)` → `stream PaymentResult` | C2 → C3 | The main task stream. C2 pushes tasks; C3 streams back results. |
| `ReportResult(PaymentResult)` → `Ack` | C3 → C2 | Final result after bank execution. Triggers C4 `WriteResult`. |
| `RevokeTask(RevokeRequest)` → `Ack` | C2 → C3 | Tells C3 to abandon task_id if still in-flight. |
| `WorkerHeartbeat(stream HeartbeatPing)` → `stream HeartbeatAck` | C3 → C2 | Bidirectional stream, ping every 2s. |

**Required proto fields on `Task`:**

```protobuf
message Task {
  string task_id         = 1;
  string idempotency_key = 2;
  double amount          = 3;
  string currency        = 4;
  string merchant_id     = 5;
  int64  epoch           = 6;  // C2 epoch — worker rejects if stale
}
```

### 3c. For Member 4 (C4 — Payment Log Service)

C3 makes exactly **two** calls into C4 per task:

| C4 RPC | Called When | What C3 Does with the Response |
|---|---|---|
| `CheckIdempotency(idempotency_key)` | **Before** calling the bank | If `exists == true`, return the cached `result` to C2. Skip the bank entirely. |
| `WriteResult(idempotency_key, result, bank_txn_ref)` | After receiving `SUCCESS` from the bank | Persists the result so future duplicate calls hit the cache. |

> **Note:** In the current design, C2 calls `WriteResult` on C3's behalf after receiving `ReportResult`. C3 does **not** call `WriteResult` directly. This avoids a race where C3 crashes between writing to C4 and reporting to C2. Coordinate with M1 and M4 if this flow changes.

**C4 address:** configured via `LOG_SERVICE_ADDR` env var. C3 must handle `UNAVAILABLE` from C4 gracefully — buffer the result in memory and retry with backoff rather than failing the payment.

| Metric | Type | Description |
|---|---|---|

| `worker_heartbeat_sent_total` | Counter | Heartbeat pings sent to C2 |
| `worker_active_tasks` | Gauge | Currently in-flight tasks |
| `worker_revoked_tasks_total` | Counter | Tasks abandoned due to REVOKE |

**Docker Image Requirements**

| Requirement | Value |
|---|---|
| Image name | `worker` |
| Exposed port (gRPC) | Dynamic — registered at startup via `RegisterWorker` |
| Exposed port (Prometheus) | `9092` |

## 4. Fault Tolerance Mechanisms

### Retry Engine

When the Mock Bank API returns a failure (HTTP 5xx or timeout), C3 retries using **exponential backoff** before giving up.

```
Attempt 1  →  bank call  →  FAIL
              wait 1s
Attempt 2  →  bank call  →  FAIL
              wait 2s
Attempt 3  →  bank call  →  FAIL
              wait 4s
              ─── retries exhausted ───
Report FAILURE to C2 (C2 → C4 writes terminal FAILURE state)
```

**Key invariant:** The **same `idempotency_key`** is used on every retry attempt. This means:

- The bank's own idempotency cache deduplicates if the first call succeeded but the response was lost in transit
- C4's `CheckIdempotency` will catch any retry that follows a worker crash mid-execution

**Do not generate a new `idempotency_key` per retry attempt.** This is the most common exactly-once bug.

---

### Idempotency: Preventing Double-Charges on Crash

The scenario M2 must test explicitly:

```
Timeline:
  T=0    Worker A calls Mock Bank → SUCCESS (bank charges customer)
  T=1    Worker A crashes before calling ReportResult
  T=5    C2 detects Worker A dead (3 missed heartbeats)
  T=6    C2 reassigns task to Worker B
  T=7    Worker B calls C4.CheckIdempotency(key) → exists=true, result=SUCCESS
  T=7    Worker B returns cached result to C2 immediately
  T=8    C2 calls C4.WriteResult with SUCCESS

Customer charged exactly once. ✅
```

The entire exactly-once guarantee hinges on **Step 2 being atomic and mandatory**. There is no code path in C3 that skips `CheckIdempotency`. If you're adding a fast path — don't.

## 5. Environment Variables

| Variable | Required | Default | Description |
|---|---|---|---|
| `COORDINATOR_ADDR` | ✅ | — | gRPC address of the current Coordinator leader (e.g. `coordinator-1:50051`). C3 will re-resolve on reconnect. |
| `LOG_SERVICE_ADDR` | ✅ | — | gRPC address of C4 Payment Log Service (e.g. `payment-log:50054`). |
| `BANK_API_ADDR` | ✅ | — | HTTP address of Mock Bank API (e.g. `http://mock-bank:8090`). |
| `BANK_FAIL_RATE` | ❌ | `0.10` | Probability (0.0–1.0) of a simulated bank failure. Override in fault injection tests. |
| `BANK_LATENCY_MIN_MS` | ❌ | `50` | Minimum simulated bank latency in milliseconds. |
| `BANK_LATENCY_MAX_MS` | ❌ | `500` | Maximum simulated bank latency in milliseconds. |
| `WORKER_ID` | ❌ | auto-UUID | Stable ID for this worker instance. Set explicitly in `docker-compose.yml` for deterministic logs. |
| `HEARTBEAT_INTERVAL_MS` | ❌ | `2000` | How often (ms) to ping C2. Must be < C2's dead timeout (6000ms). |
| `MAX_CONCURRENT_TASKS` | ❌ | `5` | Max parallel tasks this worker will accept. Reported to C2 as capacity. |
| `METRICS_PORT` | ❌ | `9092` | Port for Prometheus `/metrics` endpoint. |
| `GRPC_PORT` | ❌ | `0` (OS-assigned) | Port C3 listens on for incoming gRPC (RevokeTask, etc). Reported to C2 at registration. |
| `LOG_LEVEL` | ❌ | `info` | Log verbosity: `debug`, `info`, `warn`, `error`. Use `debug` in local dev, `info` in Docker. |
| `RETRY_MAX_ATTEMPTS` | ❌ | `3` | Max bank retry attempts before marking a task FAILURE. |
| `RETRY_BASE_DELAY_MS` | ❌ | `1000` | Base delay for exponential backoff. Delays: base, base×2, base×4. |

**Example `.env` for local dev:**

```dotenv
COORDINATOR_ADDR=localhost:50051
LOG_SERVICE_ADDR=localhost:50054
BANK_API_ADDR=http://localhost:8090
BANK_FAIL_RATE=0.10
WORKER_ID=worker-local-1
LOG_LEVEL=debug
```

## 6. Running Locally

**Standalone (dev):**

```bash
# From repo root
cd services/worker-service

go run ./cmd/worker \
  -coordinator=localhost:50051 \
  -log-service=localhost:50054 \
  -bank=http://localhost:8090
```

**Via Docker Compose (full stack):**

```bash
# Spin up the full PayFlow stack
docker-compose up --scale worker=3

# Watch a specific worker's logs
docker-compose logs -f worker-2

# Simulate worker death (triggers C2 reassignment)
docker kill payflow_worker-2_1
```

**Verify exactly-once behavior:**

```bash
# 1. Submit a payment
curl -X POST http://localhost:8080/v1/payments \
  -H "Authorization: Bearer <jwt>" \
  -d '{"amount": 100.00, "currency": "USD", "merchant_id": "m_001", "idempotency_key": "test-idem-001"}'

# 2. Kill the worker mid-flight
docker kill payflow_worker-1_1

# 3. Resubmit the same idempotency_key — should return the same txn_id
curl -X POST http://localhost:8080/v1/payments \
  -H "Authorization: Bearer <jwt>" \
  -d '{"amount": 100.00, "currency": "USD", "merchant_id": "m_001", "idempotency_key": "test-idem-001"}'

# Expected: same txn_id, no second bank charge ✅
```
